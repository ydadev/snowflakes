# Правила разработки Snowflakes

## Сначала прочитать

1. README.md.
2. docs/DEVELOPMENT_STATUS.md и docs/ROADMAP.md.
3. docs/GOAL.md, docs/TECHNICAL_SPEC.md и docs/CENTRAL_CONTROL.md.
4. docs/ARCHITECTURE.md, docs/TEST_PLAN.md и относящиеся к работе ADR.

Последнее указание пользователя имеет приоритет над документами. При изменении направления обновлять затронутые документы, удаляя противоречащие требования.

## Выполнение этапов

- Продолжать с первого незавершённого этапа ROADMAP. Разбивать работу на проверяемые задачи с его идентификаторами.
- Делать законченный проверяемый результат, а не только описывать план.
- Обновлять DEVELOPMENT_STATUS после существенного результата: что изменено, чем проверено, что осталось, следующий шаг.
- Проставлять Done только при наличии результата и требуемого подтверждения. Для непроведённых проверок использовать Not run с причиной.
- Условия завершения этапа не заменяются успешной компиляцией. Интерактивные проверки Windows и тесты на обеих ОС фиксируются отдельно.
- При недоступном стенде продолжать независимые задачи, сохраняя незавершённую проверку. Не объявлять этап или выпуск готовым.
- Решения, меняющие компоненты, протокол или поведение, фиксировать отдельным ADR.
- Сохранять авторизацию пользователя между шагами. Работу на живой инфраструктуре выполнять в рамках поручения, после подготовки и проверки нужного пакета.

## Обязательная чистота репозитория

- В Git допускается только нейтральная документация и исходники продукта.
- Не переносить в репозиторий переписку, реквизиты, реальные адреса серверов, организационные имена, внутренние домены, личные данные, пути пользовательских профилей и отчёты реальных панелей.
- Не публиковать пароли, токены, приватные ключи, рабочие конфиги, базы SQLite, логи и дампы.
- Примеры используют loopback, обозначения SERVER_IP и тестовые данные. Реальный IP задаётся при установке.
- Частные сведения размещения допустимы только в игнорируемом .local/ без паролей и токенов. Секреты передавать через подходящее защищённое хранилище; в Markdown их не записывать.
- Не добавлять .local/, .env, рабочее хранилище сайта и файлы ключей, в том числе через git add -f.
- Перед каждым коммитом проверять staged diff, список файлов и автора/почту коммита. Применять публичный noreply-адрес вместо рабочей почты.
- Перед push проверять все публикуемые файлы, коммиты, сообщения, ветки и артефакты. Проверка секретов включает известные приватные значения из контекста, но не сохраняет их в исходниках проверки и не печатает.
- Снимки и демонстрации делать на тестовом рабочем столе с синтетическими окнами и данными.

## Технические границы

- Клиент: Rust, Windows 10/11 x64, Win32 и проверяемый GPU-путь D3D11/DXGI/DirectComposition.
- Сайт: PHP 8.3+, SQLite, готовые локальные ресурсы; обычная файловая установка.
- Подключение к сайту напрямую по настраиваемому IP:порту; пример локального стенда 127.0.0.1:805.
- Профили сервера и пользователя независимы. Снятие галочки прекращает опрос и возвращает местный профиль.
- Опрос продолжает работать при выключенном сервером эффекте. Закрытый процесс не запускается запросом сервера.
- Реализация и ресурсы оригинальные; код, шейдеры и ассеты других снеговых приложений не переносить.
- FFI/unsafe локализовать, время симуляции отделять от FPS, ограничивать память и очереди.
- Не вводить брокер, дополнительную панель прокси, контейнеры или отдельный постоянно работающий backend без необходимого изменения требований.

## Проверки и изменения

Запускать проверки, соответствующие изменению. Для кода нужны значимые тесты поведения; не писать тесты, которые повторяют реализацию. Для документации проверять согласованность, ссылки, примеры и отсутствие приватных данных.

Не изменять чужую работу, глобальные настройки Git, историю или системные службы без соответствующей задачи. Коммиты должны содержать один связный результат. Не переписывать историю для оформления прогресса.
