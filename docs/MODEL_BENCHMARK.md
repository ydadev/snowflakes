# Замер снеговой модели без рабочего эффекта

Дата: 14 ноября 2026 года. Область P3-04; решение [ADR 0039](adr/0039-headless-snow-model-benchmark.md).

snow_model_bench — отдельная консольная программа. Она создаёт синтетическую сцену в памяти и вызывает настоящий World::step. Нативных окон, графики, профиля, IPC и обращения к работающему клиенту нет. Рабочий эффект остаётся в прежнем состоянии.

## Запуск

Из корня репозитория:

~~~powershell
cargo run -p snowflakes-client --release --locked --example snow_model_bench -- --scenario baseline --steps 3600 --warmup 120 --seed 24301
cargo run -p snowflakes-client --release --locked --example snow_model_bench -- --scenario material-stress --steps 3600 --warmup 120 --seed 24301
cargo run -p snowflakes-client --release --locked --example snow_model_bench -- --scenario contact-stress --steps 60 --warmup 2 --seed 24301
~~~

Запускать сценарии последовательно, без параллельной компиляции и других экспериментов. Для сохранения результата направить stdout в новый файл внутри игнорируемого .local/. Cargo пишет сообщения сборки в stderr; программа пишет один JSON-объект в stdout. Зафиксировать Git SHA исходников и SHA256 исполняемого файла отдельно от отчёта.

Параметры: baseline, material-stress или contact-stress, 60–36000 измеряемых шагов, 0–3600 шагов прогрева, ненулевой seed. По умолчанию baseline, 3600/120 шагов и seed 24301. Debug-сборка отклоняется. Проверяемый лимит 300 секунд охватывает подготовку, прогрев и измерение; проверки выполняются на границах фаз/итераций, включая конец измерения. Ошибка аргументов, API, баланса, нагрузки контактов или бюджета даёт ненулевой код выхода и короткую причину.

## Сценарии

[Локализация стоимости корней](TEST_RESULTS_MONOTONE_ROOTS.md) использует отдельную диагностическую копию; опубликованный измеритель и производственный клиент не содержат её таймеров. Числа с инструментированием не сравнивать как обычный A/B release.

| Сценарий | Вход |
| --- | --- |
| baseline | Один 1920×1080 при 100%, десять окон, интенсивность 50%, накопление 35%; начальные 1 DIP на крышах и 2 DIP внизу, обычные силы/эмиссия/таяние |
| material-stress | Два 3840×2160 при 200%; 4800 активных связных тел из закрытых источников, затем 252 закрытия наполненных крыш, 128 записей очереди; интенсивность 0, накопление 100%, таяние выключено |
| contact-stress | Два 3840×2160 при 200%, 16 принимающих окон и 4800 связных тел у крыш; каждый независимый эпизод содержит один настоящий шаг, после него проверяется перенос массы |

material-stress повторяется через 120 шагов. Во время его физических шагов обычных окон уже нет; это проверка тяжёлого материала с нижними опорами. contact-stress заново готовится перед каждым шагом, включая прогрев, и требует минимум 90% уменьшения количества тел вместе с минимум 25% массы на принимающих крышах. Наличие только outflow, пустой второй шаг или неполные наблюдения отклоняются. Эти пересоздания измеряются отдельно и входят в CPU/время измеряемого интервала. Поле fixture описывает подготовку, observed — выборочные состояния, contact_activity — подтверждение каждого контактного шага. [Решение и результаты](TEST_RESULTS_CONTACT_WORKLOAD.md).

Симуляция выполняется без реальных пауз между шагами. Сумма 3600×DT составляет 60 секунд физических шагов; эпизодические сбросы сохраняются, контактная нагрузка состоит из независимых одношаговых приземлений. Замер занимает другое реальное время. Прогрев относится к коду и распределению памяти, тепловой режим стенда проверяется отдельно.

## Содержание JSON

В observed.peak.max_active_bodies указан максимум наблюдавшегося текущего порога допуска, а global_max_active_bodies сообщает абсолютную границу активных тел 16 000. После уменьшения числа экранов сохранённых тел может быть больше нового порога; проверка сравнивает их с абсолютной границей. Новое поле не входит в отпечаток состояния. Ожидающие части/профили учитываются отдельно. [Решение и тесты](TEST_RESULTS_GLOBAL_BUDGET.md).

- step_time: среднее, p50/p95/p99/max в микросекундах, число вызовов и превышений DT. Подготовка и наблюдение исключены из каждого таймера.
- reset_time и initial_setup_us: построение синтетической нагрузки; отдельные распределения не смешиваются с физическими шагами.
- process: CPU измеряемого интервала, его реальные длительности, доступные логические процессоры, private bytes/working set до и после. Пики памяти — за жизнь процесса до последнего снимка, включая прогрев, подготовку, World и буферы инструмента.
- observed: выборочные максимумы активных тел, ячеек, ожидающих пакетов/частей, масок и минимум активного пула. Снимки выполняются через 30 шагов и на границах эпизодов. Это наблюдённые максимумы, не непрерывная трасса.
- validation подтверждает только проверенные счётчики и баланс с допуском 0,1%; product_performance_acceptance остаётся not_run.
- Только contact-stress добавляет contact_activity: число наблюдений, минимальные начальные тела/их чистое уменьшение, прирост массы крыш, его долю, суммы по эпизодам, outflow и ошибку баланса. Полное число samples должно совпасть с measured_steps. validation.contact_load=passed означает проверенную нагрузку контактов. Подготовка/проверка находятся вне step_time; прежние поля и отпечатки baseline/material-stress сохраняются.

После [проверки преобразований](TEST_RESULTS_TRANSFORM_REUSE.md) observed дополнен state_hash_version и sampled_active_and_drift_hash. Отпечаток версии 1 включает биты активных состояний/контуров, mass/pending ячеек опор и счётчики на точках наблюдения. Он некриптографический, не включает все скрытые поля World и не заменяет проверки поведения. Сравнивать его при одинаковых сценарии, seed, сборочной среде и наблюдателе. Снятие исключено из времени шага, но входит в CPU процесса.

CPU вычисляется из разности суммарного времени потоков процесса [GetProcessTimes](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocesstimes). В него входят пересоздание сцены и наблюдение. Процент нормирован по указанному available_logical_processors и относится к непрерывно вычисляющему эксперименту; с пределом 3% для обычного клиента его не сравнивать.

Память читается через [GetProcessMemoryInfo](https://learn.microsoft.com/en-us/windows/win32/api/psapi/nf-psapi-getprocessmemoryinfo): PrivateUsage, WorkingSetSize, PeakPagefileUsage и PeakWorkingSetSize из [PROCESS_MEMORY_COUNTERS_EX](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex). Это память отдельного процесса модели. GPU/DWM и изображение не измеряются; private bytes не равны размеру одного World. На других ОС нативные значения null с явной причиной.

## Первый локальный результат

Windows 11 x64, Rust 1.99.1/MSVC, release, 28 доступных логических процессоров. Один последовательный прогон каждого сценария, seed 24301, 120 шагов прогрева и 3600 измеряемых шагов. Эталонная аппаратная приёмка ТЗ остаётся открытой.

| Метрика | baseline | material-stress |
| --- | --- | --- |
| Среднее физического шага | 0,091 мс | 9,007 мс |
| p95 физического шага | 0,118 мс | 12,084 мс |
| Максимум | 0,335 мс | 23,403 мс |
| Шагов дольше DT из 3600 | 0 | 23 |
| Наблюдённые активные тела | 309–383 | 4800–4800 |
| Максимум ожидающих частей | 0 | 812 в 128 пакетах |
| Наблюдённые ячейки активных/ожидающих профилей | 0 / 0 | 40814 / 12279 |
| CPU измеряемого интервала | 0,328 с | 32,703 с |
| Реальное время с пересозданиями и наблюдением | 0,328 с | 33,888 с |
| Среднее пересоздания | нет | 50,321 мс, 29 пересозданий |
| Пик private bytes за жизнь процесса | 1,29 МиБ | 4,98 МиБ |

Максимальная относительная ошибка баланса: около 0,000934% и 0,000000715% соответственно, ниже проверяемого допуска 0,1%. Нагрузочный сценарий показывает заметные затраты физики и отдельные шаги дольше DT; причины требуют локализации перед оптимизацией. Одного прогона недостаточно для выводов о разбросе между запусками.
