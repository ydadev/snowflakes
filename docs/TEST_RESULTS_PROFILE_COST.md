# Измерение стоимости графических профилей снега

Дата: 14 ноября 2026 года. Среда: Windows 11 x64, Rust 1.99.1/MSVC, аппаратный D3D11, один адаптер/собственный target. База production-пути — 6d53eb1; метод — [ADR 0050](adr/0050-hidden-profile-cost-experiment.md). Модель адаптера/версия драйвера в этом прогоне не записаны; числа относятся к данному опыту.

## Воспроизведение

Из подготовленной среды разработки, без параллельной компиляции/замеров:

```powershell
cargo test -p snowflakes-client --lib native_profile_cache_cost_without_presentation --release --locked -- --ignored --nocapture
```

Эксперимент ignored по умолчанию; debug-запуск отвергается. Создаётся собственный скрытый слой 1280 × 720. ShowWindow/Present и IPC-команды работающему клиенту не вызываются. Выходные записи начинаются с profile_cost и содержат JSON schema_version=2. Сырые журналы остаются локальными; в Git публикуются только нейтральные результаты.

## Проверка метода

Три обычных сценария Passed: S_FALSE/ошибки не считаются готовыми, недостоверные timestamp не превращаются в числовое время; nearest-rank перцентили и отказ для пустых/нечисловых данных; независимое изменение позы/формы и повторяемость фикстуры.

Полный tools/check.ps1 Passed: 338 тестов клиента (98 библиотечных), 3 protocol, 35 утверждений ресурсов и 31 кадров, fmt/clippy, release, baseline smoke модели, Ajv/PHP/SQLite/HTTP. Четыре нативных сценария исключены из обычного прогона. Прежний GPU-сценарий масок/градиентов дополнительно Passed в release: 48 случаев, прежние максимумы AA и нулевое расхождение вне краевой полосы. Это отдельная проверка после изменения общего reference helper.

Коммит 71a03a2b1adafa7d661973f8534e0f7a32b9808f прошёл [GitHub CI](https://github.com/ydadev/snowflakes/actions/runs/43566751191): Windows 5 мин 4 с, contract-and-php 18 с. Журнал подтвердил 338 тестов клиента, 3 protocol, четыре ignored и обе версии PowerShell 7/5.1 для ресурсов/кадров. Read-only статус существующего клиента подтвердил manual и rendering=false; сборка и измерения не заменяли рабочий процесс.

Явный нативный опыт Passed за 22.61 с: три нагрузки × шесть блоков × 80 кадров = 1440 измеряемых кадров, ещё 16 прогревочных перед каждым блоком. В каждом GPU-query обнаружено pixel shading, все 1440 timestamp-интервалов достоверны. До временных блоков сравнение синтетических пикселей с прежним рендером подтвердило заливку/покрытие вне краевой полосы 1.5 px и раздельные контуры. Обе копии одной нагрузки дали одинаковый отпечаток финальных форм/поз для всех трёх вариантов.

На каждой сцене девять сугробов, пласты имеют по 24 ячейки с пустым промежутком. moving16/moving128 меняют позиции и углы 16/128 пластов при неизменной форме. changing128 дополнительно меняет высоты всех пластов и сугробов каждый кадр. Это синтетическая нагрузка рендерера, не интеграция выпадения/баланса массы.

В порядке reference/paths/realizations/realizations/paths/reference сохранены два повтора каждого варианта. Ниже mean обоих повторов в миллисекундах; p95 тоже дан отдельно, без усреднения перцентилей. CPU wall — длительность вызова рендерера с Direct2D/driver/возможными ожиданиями; GPU interval — прошедший интервал команд, не busy time.

В moving16 за блок эталон создал 2000 путей, кеши получили 2000 попаданий и не строили новые после прогрева. В moving128 — 10 960 путей эталона против 10 960 попаданий. В changing128 каждый кеш построил и вытеснил по 10 960 профилей, попаданий нет, реализаций GPU не создавал: действительно проверена постоянно меняющаяся форма. Удерживалось не более 137 записей/77 336 условных точек.

Для небольшой движущейся сцены wall-время подготовки ниже у кешей. На тяжёлой неизменной сцене realizations снижают измеренный CPU wall, одновременно увеличивая GPU-интервал примерно на 19%; на небольшой — примерно на 26%. Минимальное число pixel-shader invocations также выше: около 0.633 млн против 0.461 млн для moving16 и 3.256 млн против 2.609 млн для moving128. Это сопутствующее наблюдение; конкретная причина ещё не изолирована.

Changing128 не подтверждает устойчивого ускорения, разброс CPU wall заметен. Вспомогательное thread CPU содержит обновление фикстуры/опрос и имеет наблюдаемую крупную дискретность. Completed wall включает задержки опроса. Они сохранены в JSON, но не используются как доказательство чистого CPU/GPU времени или экранной задержки.

Первый прототип метода с двумя вариантами также Passed, но дал сильный разброс CPU. Финальный метод заранее прогревает/проверяет оба кеша, выносит bitmap readback из порядка временных блоков, получает factory вне таймера и подтверждает pixel shading. Его числа не смешиваются с прототипом. Результат требует дальнейшего исследования политики кеша, не подтверждает общий прирост FPS и не меняет production-путь автоматически.

## Непроведённая приёмка

| Область | Результат | Причина |
| --- | --- | --- |
| Чистое GPU busy time, VRAM и энергия | Not run | Измерен timeline с возможными промежутками, не занятость движков/видеопамять |
| DWM/S_OK Present, реальный FPS, CT-10 | Not run | Present и видимый эффект не запускались |
| Полный клиент, физика, IPC/трекер и несколько экранов | Not run | Изолированы только графические профили одного target |
| Windows 10, разные GPU/драйверы, device lost и восемь часов | Not run | Один стенд и короткий опыт |
| Полная приёмка EN-09/P3 | Not run | Нужны дальнейшая изоляция затрат и разрешённые нативные проверки |

Рабочий эффект остаётся на ручной паузе. Дождь, лужи, сайт и поставка отложены.
