# Журнал ошибок получения общей сцены

Дата: 16 ноября 2026 года. Область: P2, F1 [сводного аудита](SNOW_CLIENT_AUDIT.md), ненумерованное требование локального сохранения ошибок. Решение: [ADR 0092](adr/0092-scene-query-fault-journal.md).

## Что изменилось

Tracker::poll_source теперь передаёт числовой код перехваченного отказа непосредственно в Recorder. Запись не зависит от наблюдения промежуточного Report. Worker привязывает существующий optional журнал до первого опроса. Повтор того же неустранённого кода подавляется, иной код и отказ после успешной сцены дают новое событие. Возврат ошибки в виде scene_pending, повтор 100 мс и полное обновление сцены сохранены; GPU Recovery и физика не менялись.

После подготовки привязки Recorder, но до изменения прежней ветки Err(_), новая регрессия Failed: при первом отказе enqueued=0 вместо 1 с сообщением scene failure was not journaled. Это воспроизведение перехваченной ошибки с подготовленной привязкой, а не запуск неизменённой старой сборки. После добавления записи все три адресные проверки Passed в debug.

| Проверка окончательных исходников | Результат |
| --- | --- |
| Три проверки scene::tests::fault_log | Passed в debug/release |
| tools/check.ps1 | Passed: 548 + 3 + 8 выполнений Rust, 47 ignored |
| CI окончательных исходников | Pending |

## Независимые условия

Проверяется настоящий Tracker/Registry::poll на управляемом Source без HWND, WinEvent-hooks, реестра Windows, IPC или GUI. Опросы используют заданные монотонные отметки времени; это не замер реальной задержки. Отказ order и отказ screens возвращают разные HRESULT. Последовательные повторы одного кода не добавляют события, включая повтор после refresh; изменение кода добавляет. Ожидание до 100 мс не вызывает Source. После успешного снимка тот же код записывается снова. Итоговая история хранит три ожидаемых числовых события даже после наблюдаемого восстановления.

Отдельный сценарий проверяет оба вида периодического отказа после исправной сцены. Изменения рамки и нижней границы без событий должны появиться после восстановления, key окна остаётся прежним, полный reread не теряется и следующий секундный срок сверки сохраняется. Оба последовательных отказа дают одну запись за эпизод.

Error с синтетическим приватным сообщением оставляет в JSONL только фиксированный вид/числовой HRESULT: текст, временный путь и данные окна отсутствуют. Исправный начальный и периодический опрос не создают каталог истории. В журнал не добавляются ни новая схема IPC, ни содержимое сцены.

## Общие регрессии и ограничения

Окончательный tools/check.ps1 Passed: fmt/clippy, 548 тестов клиента + 3 протокола + 8 release-повторов — 559 выполнений и 551 уникальная проверка Rust; 47 ignored, библиотечный набор 235. Восемь прежних smoke-отпечатков и границы массы/пулов сохранены. Три новые проверки отдельно Passed в release. Сборщики 35/31 assertions прошли в одной локальной редакции PowerShell; schema 60, PHP 60+5, SQLite/HTTP прошли как прежние регрессии компонентов. Разработка воды/сайта не возобновлялась.

При ревью первый тест уточнён: сразу после refresh он должен повторить прежний HRESULT и сохранить одну запись, только затем сменить код. Окончательный общий прогон и release выполнены после этой правки. Отдельные нативные GPU/Worker-пробы не повторялись: интерфейсы запуска и графический путь не менялись. Прежние проверки безопасного scene_pending, независимых пауз, полного обновления Registry и ограниченного GPU Recovery входят в общий набор.

Настоящие сбои EnumWindows/DWM/дисплеев не вызывались. Управляемый Source не заменяет реальный Worker/видимый вывод, Windows 10/11 целиком, mixed DPI/hotplug, другие роли/сеансы, ресурсы и восьмичасовой прогон. Прежний редкий ERROR_BUSY тестового desktop не исправлен этим изменением. Пределы и возможные потери записи сохраняются по ADR 0090.

F1 реализован и проверен в указанном управляемом объёме; P1/P2/P3 и итоговая приёмка не закрываются. Следующая независимая работа — F2: автоматическое снижение графического качества с проверяемым основанием, гистерезисом и сохранением физического профиля/массы. Настоящие две 4K остаются отдельной приёмкой. Рабочий клиент не заменялся и не включался; read-only статус подтвердил manual/rendering=false. Вода, сайт и поставка отложены, полная цель активна.

## Повторение

~~~text
cargo test -p snowflakes-client --lib --locked platform::scene::tests::fault_log -- --nocapture
cargo test -p snowflakes-client --release --lib --locked platform::scene::tests::fault_log -- --nocapture
~~~

Эти команды используют управляемую геометрию и временный журнал; рабочий снег не запускается.
